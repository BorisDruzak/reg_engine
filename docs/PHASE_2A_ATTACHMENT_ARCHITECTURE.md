# Phase 2A Attachment Architecture

Phase 2A defines the storage architecture for card-level attachments. It does not add backend models, migrations, upload endpoints, download endpoints, public-link file behavior, or frontend UI.

## Approved Scope

- Card-level attachments first.
- Generated documents are deferred.
- Local filesystem backend through a storage abstraction.
- Storage root and operational settings are configured outside Git.
- Public links cannot upload attachments in the first Phase 2 slice.
- Public links cannot download attachments in the first Phase 2 slice.
- `file_ref` is deferred until attachment metadata is stable.
- Malware scanning enforcement is deferred in Phase 2A, but a scanner hook is required before upload endpoints are exposed.
- Archived attachments are hidden from normal active lists, preserved, and readable only as read-only archive records by actors who can read the card in the relevant scope.

## Metadata Schema Design

The first future migration should add metadata tables only. Binary file contents are stored by `AttachmentStorage`, not in Git and not directly in Core Schema v1 card value columns.

### `stored_files`

One row represents one stored binary object.

| Column | Type | Required | Notes |
| --- | --- | --- | --- |
| `id` | UUID | yes | Primary key. |
| `storage_backend` | string | yes | First value: `local_filesystem`. |
| `storage_key` | string | yes | Opaque key generated by service; unique; never a user filename. |
| `original_filename` | string | yes | Display metadata only; sanitized for UI. |
| `content_type` | string | yes | MIME type from validated upload metadata. |
| `content_length_bytes` | bigint | yes | Must be greater than zero and within configured limit. |
| `checksum_sha256` | string | yes | Hex SHA-256 of stored bytes. |
| `scanner_status` | string | yes | `deferred`, `pending`, `clean`, `blocked`, or `error`. |
| `scanner_checked_at` | timestamptz | no | Set when a scanner returns a non-deferred result. |
| `scanner_details_json` | json | no | Non-secret scanner metadata; no raw file content. |
| `created_by` | UUID | yes | FK to `users.id`. |
| `created_at` | timestamptz | yes | Server timestamp. |
| `archived_at` | timestamptz | no | Metadata archive marker; binary is not physically deleted by normal workflow. |
| `archived_by` | UUID | no | FK to `users.id`. |
| `archive_reason` | string | no | Operator-visible archive reason. |

Required constraints and indexes:

- unique index on `storage_key`;
- index on `checksum_sha256`;
- check `content_length_bytes > 0`;
- check `scanner_status in ('deferred', 'pending', 'clean', 'blocked', 'error')`;
- no cascade delete from cards or users.

### `card_attachments`

One row links a stored file to one card.

| Column | Type | Required | Notes |
| --- | --- | --- | --- |
| `id` | UUID | yes | Primary key. |
| `card_id` | UUID | yes | FK to `cards.id`. |
| `stored_file_id` | UUID | yes | FK to `stored_files.id`. |
| `title` | string | yes | Russian UI can show this as attachment title; defaults from original filename. |
| `description` | string | no | Optional user-entered description. |
| `position` | integer | yes | Stable order inside a card. |
| `created_by` | UUID | yes | FK to `users.id`. |
| `created_at` | timestamptz | yes | Server timestamp. |
| `archived_at` | timestamptz | no | Link archive marker. |
| `archived_by` | UUID | no | FK to `users.id`. |
| `archive_reason` | string | no | Operator-visible archive reason. |

Required constraints and indexes:

- index on `card_id`;
- index on `stored_file_id`;
- index on `(card_id, archived_at)`;
- check `position >= 0`;
- no physical delete as normal workflow.

### Deferred Metadata

These tables and fields are not part of the first attachment backend slice:

- `document_templates`;
- `generated_documents`;
- `field_values.value_file_id`;
- `field_value_items.value_file_id`;
- public-link upload/download tables.

When `file_ref` is introduced later, it should reference `card_attachments.id` or a dedicated card-scoped file reference, not raw filesystem paths and not unscoped storage keys.

## Service Boundary

Phase 2B should introduce service interfaces before API routes.

### `AttachmentStorage`

Responsibilities:

- generate opaque storage keys;
- write a stream or bytes to backend-owned storage;
- return byte count and checksum data needed for metadata validation;
- open a stored object for authorized reads;
- verify a key exists for smoke tests;
- reject path traversal and absolute paths.

The local filesystem backend reads its root from external configuration such as `REG_ENGINE_STORAGE_ROOT`. It must write under that root only. It must never derive storage paths from `original_filename`.

### `AttachmentService`

Responsibilities:

- validate upload metadata before storage;
- authorize create/read/download/archive through existing card visibility and edit rules;
- create `stored_files` and `card_attachments` metadata in one service workflow;
- record audit events for create, archive, and download when download becomes available;
- preserve metadata and file bytes during archive;
- reject writes to archived or superseded cards unless a later plan explicitly allows an archive-only workflow.

### `MalwareScanner`

Responsibilities:

- accept a stored object or temporary upload location;
- return one of `deferred`, `pending`, `clean`, `blocked`, or `error`;
- provide non-secret details suitable for `scanner_details_json`;
- allow a default `DeferredMalwareScanner` in MVP/internal staging.

Phase 2A defers enforcement. Before upload endpoints are exposed, the upload service must call the `MalwareScanner` hook and persist `scanner_status`. A later security checkpoint can change policy from `deferred allowed` to `clean required` without changing the metadata schema.

## Access-Control Rules

Users can create attachments only for cards they can edit.

Users can read or download attachments only for cards they can read.

Users can archive attachments only for cards they can edit.

Archived attachments are hidden from normal active attachment lists. Archive does not physically delete metadata or stored bytes. Archive-scope reads may return archived attachment metadata and, when download endpoints exist, archived binary content as read-only records to actors who can read the card. Archived attachments cannot be edited, replaced, or reattached through the normal workflow.

Organization scope is inherited from the card:

- org admins can act inside their own organization and descendants when their grant includes descendants;
- org admins cannot access parent or sibling branches through attachments;
- registry-level permissions do not bypass organization scope.

Superseded cards are readable in archive scope, but not editable. Attachments on superseded cards are read-only unless a later plan adds a specific archive-management operation.

Public links cannot upload attachments in the first Phase 2 slice.

Public links cannot download attachments in the first Phase 2 slice.

Public-link edit remains limited to direct field editing already allowed by the public-link card rules.

## Audit Rules

Future attachment services must write `audit_events` for:

- attachment metadata creation;
- attachment archive;
- attachment download when download endpoints are introduced;
- scanner status transitions if scanning becomes asynchronous.

Suggested future `audit_events.object_type` values:

- `stored_file`;
- `card_attachment`.

Suggested future `audit_events.action` values:

- `attachment_create`;
- `attachment_archive`;
- `attachment_download`;
- `attachment_scan_update`.

## Storage Configuration

No storage root, filesystem path, bucket name, endpoint, credential, or internal hostname may be committed to Git.

Expected future settings:

| Setting | Purpose |
| --- | --- |
| `REG_ENGINE_STORAGE_BACKEND` | First value: `local_filesystem`. |
| `REG_ENGINE_STORAGE_ROOT` | Absolute server-local storage root outside the repository. |
| `REG_ENGINE_MAX_ATTACHMENT_BYTES` | Upload size limit enforced before storage. |
| `REG_ENGINE_ATTACHMENT_ALLOWED_TYPES` | Optional comma-separated allow-list for MIME types. |
| `REG_ENGINE_MALWARE_SCANNER` | First value may be `deferred`; future values can select a scanner implementation. |

The configured root should be backed up with the database metadata. It should not live under the Git checkout.

## Required Phase 2B Tests Before Upload Endpoints

Phase 2B must add automated tests with these behaviors before any upload endpoint is exposed:

- `test_create_attachment_metadata_requires_editable_card`;
- `test_read_attachment_metadata_requires_readable_card`;
- `test_archive_attachment_preserves_file_metadata_and_writes_audit`;
- `test_archived_attachment_is_hidden_from_default_active_list`;
- `test_archived_attachment_is_readable_in_archive_scope_for_card_reader`;
- `test_public_link_cannot_upload_or_download_attachment`;
- `test_storage_key_rejects_path_traversal`;
- `test_malware_scanner_hook_records_deferred_status`;
- `test_attachment_metadata_rejects_empty_file`;
- `test_attachment_metadata_rejects_oversized_file`;
- `test_attachment_metadata_records_checksum_sha256`;
- `test_descendant_admin_can_read_child_card_attachment`;
- `test_sibling_admin_cannot_read_card_attachment`;
- `test_superseded_card_attachment_is_read_only`.

Phase 2A is ready for user acceptance when:

- ADR 0005 is accepted;
- this architecture document defines metadata schema, service boundary, access rules, scanner hook, and required Phase 2B tests;
- `PLANS.md` records the approved Phase 2 scope and marks Phase 2A as ready for user acceptance;
- project map is updated;
- local checks pass;
- no backend models, migrations, endpoints, upload flows, download flows, or frontend document UI were added.
