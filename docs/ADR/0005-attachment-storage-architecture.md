# ADR 0005: Attachment Storage Architecture

## Status

Accepted

## Context

Phase 2 implementation was approved on 2026-06-28 with a narrow first slice:

- card-level attachments first;
- generated documents are deferred;
- local filesystem backend through a storage abstraction;
- storage configuration stays outside Git;
- public links do not upload or download attachments in the first Phase 2 slice;
- `file_ref` is deferred until attachment metadata is stable;
- malware scanning enforcement is deferred in Phase 2A, but the scanner hook must be designed before upload endpoints are exposed.

The existing Core Schema v1 remains schema-driven. Attachments must not become a hardcoded HR or employee document model.

## Decision

Use an attachment metadata model plus a storage abstraction.

The first storage backend is a local filesystem backend configured outside Git. Runtime paths, storage roots, and operational retention settings must come from environment variables or an external runtime env file, not from committed defaults.

The first product scope is card-level attachments. A file becomes visible through a card attachment link and card visibility rules. The stored binary object is not directly addressable by users.

Generated documents, templates, public-link upload/download, and `file_ref` fields are not part of the first implementation slice.

No upload endpoints or frontend UI are introduced by Phase 2A. Phase 2A records the storage decision, metadata schema, service boundary, access-control rules, scanner hook, and tests that must exist before upload endpoints are exposed.

Phase 2H follow-up: public-link attachment list/upload/download is now an
approved later slice for active public edit links. It reuses the same
card-level attachment metadata, storage abstraction, scanner hook, bounded
upload reads, filename normalization, storage cleanup, and safe download
headers. It does not add public archive/delete, generated-document workflows,
template management, `file_ref`, PDF conversion, import/export, MCP, or a new
migration.

## Storage Boundary

Future backend code should introduce an `AttachmentStorage` boundary with these responsibilities:

- generate opaque storage keys;
- write binary content to a backend-owned storage location;
- open stored content for authorized reads;
- check existence and metadata needed for smoke tests;
- never trust user filenames as filesystem paths;
- never expose concrete storage roots in API responses, Git, or browser UI.

The local filesystem implementation must store files under a configured root such as `REG_ENGINE_STORAGE_ROOT`. The storage key should be opaque and generated by the service, for example `attachments/<yyyy>/<mm>/<uuid>`. Original filenames are metadata only.

## Metadata Boundary

Future database metadata should use two concepts:

- `stored_files`: one stored binary object and its immutable technical metadata;
- `card_attachments`: the card-scoped link, display metadata, archive state, and audit actor fields.

The metadata schema is defined in `docs/PHASE_2A_ATTACHMENT_ARCHITECTURE.md`.

## Access Boundary

Attachment authorization follows card authorization:

- create attachment metadata only when the actor can edit the card;
- read or download only when the actor can read the card;
- archive only when the actor can edit the card;
- hide archived attachments from normal active lists while preserving them as read-only archive records;
- public links cannot upload or download attachments in the first Phase 2 slice.

For Phase 2H, a public link may list, upload, and download active attachments
only when the link is active, not expired, `can_edit=true`, and the linked card
has `public_edit_enabled=true`. Archived and superseded cards remain blocked.
Public-link attachment responses must not expose
`stored_file_id`, `checksum_sha256`, storage keys, storage roots, or filesystem
paths. Public upload/download actions write `audit_events` with
`actor_type=public_link`.

Phase 2I separates field-edit usage from attachment-upload usage. `max_uses` /
`used_count` apply to public field edits. `max_attachment_uploads` /
`attachment_upload_count` apply to public attachment uploads. Successful upload
increments only `attachment_upload_count`; list/download do not increment usage
counters.

Phase 2J makes `max_attachment_uploads` configurable through the authenticated
public-link create API. Existing public-link settings remain create-only in this
slice; no PATCH endpoint is added, so changing a limit requires disabling and
recreating the link. Public attachment upload quota consumption locks and
refreshes the `card_public_links` row before checking/incrementing
`attachment_upload_count`, preventing stale-session and parallel upload races
from exceeding the configured limit.

Frontend visibility is only a UX hint. Backend services and API routes must enforce the rules.

## Malware Scanner Hook

Phase 2A defers malware scanning enforcement. This creates a known risk: if upload endpoints are exposed before a scanner hook is called and recorded, the system could store untrusted files without a review trail.

Before upload endpoints are exposed, the backend must have a `MalwareScanner` service boundary. The first implementation may return a `deferred` result, but the attachment metadata must record scanner status so enforcement can be tightened without changing the attachment schema.

## Consequences

- MVP/internal staging can use simple local storage without cloud credentials.
- Future S3-compatible storage can be added behind the same storage boundary.
- Database backups remain focused on metadata; binary backups are handled at the storage-root level.
- Phase 2B must add models, migrations, services, and tests before exposing upload endpoints.
- Phase 2D UI must stay Russian-first and must not expose raw storage keys or filesystem paths.
