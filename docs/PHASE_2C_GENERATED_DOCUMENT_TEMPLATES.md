# Phase 2C Generated Document Templates

Phase 2C adds the backend foundation for generated `.docx` documents. It does
not add frontend UI, public-link file flows, PDF conversion, import/export,
MCP, MDB migration, or service desk integration. Phase 2J.6 later added
`file_ref` text rendering to the existing `docx_text_v1` renderer.

## Metadata Schema

### `document_templates`

One row describes one active or archived template for a registry.

Important columns:

- `registry_id`
- `code`
- `name`
- `description`
- `template_format`
- `template_body`
- `output_filename_template`
- `output_content_type`
- `is_active`
- `created_by`
- `updated_by`
- `archived_at`
- `archived_by`
- `archive_reason`

The accepted Phase 2C `template_format` is `docx_text_v1`.

### `generated_documents`

One row describes one generated document for a card.

Important columns:

- `card_id`
- `template_id`
- `stored_file_id`
- `title`
- `output_filename`
- `content_type`
- `render_status`
- `generated_by`
- `archived_at`
- `archived_by`
- `archive_reason`

Generated output bytes are stored through `stored_files` and the storage
abstraction. Normal workflow is archive, not physical delete.

## Renderer

`docx_text_v1` is a constrained renderer. It accepts a text template body,
resolves placeholders from schema-driven card data, and packages the rendered
text into a minimal `.docx` file.

Supported placeholders:

- `{{ card.id }}`
- `{{ card.display_name }}`
- `{{ card.registry_id }}`
- `{{ card.organization_id }}`
- `{{ fields.<block_code>.<field_code> }}`

Unsupported placeholders fail generation. The renderer does not evaluate Python,
SQL, shell commands, Jinja expressions, or arbitrary code.

The default output filename template is `{{ card.display_name }}.docx`.

`file_ref` fields render as safe attachment text only. Active references render
as attachment title plus original filename when they differ, for example
`Скан заявления (statement.pdf)`. Empty `file_ref` values render as empty text.
Archived referenced attachments keep rendering metadata with an `(архив)`
marker. The renderer does not embed attachment binaries or add download URLs for
`file_ref`.

## Service Boundary

### `DocumentService`

Responsibilities:

- create document templates;
- archive document templates;
- generate `.docx` documents from schema-driven card data;
- create `stored_files` and `generated_documents` metadata;
- delete newly written generated bytes if metadata persistence fails;
- read generated document content for actors who can read the card;
- archive generated documents while preserving stored file metadata and bytes;
- write audit events for template create/archive and document generate/archive.

Generated files use storage prefix `generated_documents`.

## Access Rules

Template create/archive requires `registry.schema.manage`.

Document generation and generated document archive require `cards.manage` in the
card organization and registry scope.

Generated document content reads require normal card visibility.

Archived and superseded cards cannot generate new documents. Archived generated
documents remain readable only through archive scope.

Public links cannot generate, upload, or download documents in Phase 2C.
