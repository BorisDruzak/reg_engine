# Compact field and reference editor design

Date: 2026-07-11

Status: approved for implementation planning

## Goal

Simplify the card-layout field editor without changing the schema-driven data
model or breaking existing fields. The compact editor must expose only the
settings needed in the current workflow, treat field descriptions as data-entry
hints, group public-link settings, and let an administrator create or maintain
a reference list without leaving the field being edited.

## Scope

This change covers:

- the inline field editor opened from the card-template web layout;
- hint rendering in authenticated and public card-filling controls;
- inline reference-list creation and maintenance for `select` and
  `multi_select` fields;
- focused component and integration tests;
- live browser verification on the deployed administrator surface.

It does not change database tables, REST payload shapes, backend access rules,
the full `Справочники` workspace, or the meaning of archived reference lists
and items.

## Compact field editor

The default field screen contains, in order:

1. `Название поля`;
2. `Тип поля`;
3. `Подсказка` for editable field types;
4. `Обязательность` with only `Необязательное поле` and `Обязательное поле`;
5. reference-list selection and reference actions when the type is `Выбор` or
   `Множественный выбор`;
6. a collapsed `Публичное редактирование` section;
7. the existing collapsed `Ещё` section;
8. `Сохранить` and `Отмена`.

The technical code is not rendered. The existing code remains in the field
draft and is sent unchanged when the field is saved. Code generation for newly
created fields continues to use the existing schema-builder behavior. No new
technical-code editing surface is introduced.

`Описание поля` is replaced by a single-line `Подсказка` control. It continues
to read and write the existing `description` property, so no API or data
migration is required. Static text fields keep their dedicated `Текст` control
and do not show a data-entry hint or mandatory setting because they are not
fillable fields.

## Mandatory-field behavior

The UI has one mandatory state rather than separate strict and publish-time
labels:

- `not_required` is shown and saved as `Необязательное поле`;
- both legacy `required` and `required_on_publish` are shown as
  `Обязательное поле`;
- saving a mandatory field writes `required_on_publish`.

This preserves backend compatibility while aligning the editor with automatic
card lifecycle behavior: an empty mandatory value is allowed in a draft, and
the card becomes active when all mandatory values are filled. Existing strict
`required` fields retain their stored value until that field is edited and
saved through this compact editor.

## Public editing section

The two existing settings move into a closed-by-default `details` section named
`Публичное редактирование`:

- `Видно в публичной ссылке`;
- `Доступно для публичного редактирования`.

Their stored values and backend enforcement are unchanged. Static text fields
continue to force public editing off through the existing field-type rules.

## Reference-list flow

For `select` and `multi_select` fields, the field screen shows the active
reference-list selector plus these contextual actions:

- `Создать новый` is always available when reference editing is permitted;
- `Изменить выбранный` is available when an active reference list is selected.

Either action replaces all field-editor content with an inline reference
screen inside the same field rectangle. The field draft remains mounted in the
parent component. `Назад` restores the field screen with its unsaved name,
type, hint, mandatory, public, and additional settings intact.

While the reference screen is open, click-away must not commit or close the
field editor. Navigation back is explicit so an unfinished reference edit
cannot silently save or discard the field draft.

### Create mode

Create mode contains:

- a heading `Новый справочник`;
- `Название справочника`;
- `Создать справочник`;
- `Назад`.

The technical code is generated by the existing unique-code helper. Empty-name
submission shows `Введите название справочника`; the action is not silently
disabled. On success, the new list is selected for the field, reference-list
queries are refreshed, and the screen switches to selected-list management.

### Selected-list mode

Selected-list mode contains:

- the list name with a rename action;
- its active items in saved order;
- add, rename, reorder, and archive actions for items;
- `Назад`.

The compact editor uses the existing reference-list and reference-item REST
endpoints. Organization ownership, descendant inheritance, system-management,
and list archival remain in the full `Справочники` workspace and are not
duplicated here. A system-managed or otherwise backend-denied list remains
readable; denied mutations show the existing localized error instead of raw
service text.

## Hint rendering while filling a card

The hint is visible only in editing/filling controls, not as an extra metadata
block in read-only card rendering.

- Text and number inputs use the hint as `placeholder`.
- Select controls use it as the empty, non-value prompt.
- Multi-select controls show it inside the control area before the available
  choices.
- Date, date-time, boolean, reference, file, and other controls that cannot
  reliably display a native placeholder show a compact hint immediately under
  the control within the same field-input area.
- If `description` is empty, no placeholder or hint is rendered.

The same behavior applies to authenticated block editing and public-link card
editing. It does not weaken backend validation or public-field visibility
checks.

## Component boundaries and data flow

- `InlineFieldEditor` owns the field draft and the active screen
  (`field`, `create-reference`, or `manage-reference`).
- A focused `InlineReferenceEditor` owns temporary reference-list/item form
  state and mutations. It receives the token, registry id, selected list, and
  callbacks rather than duplicating card-layout state.
- `CardLayoutStudio` supplies registry context and refreshes the existing
  reference-list query after create or update.
- A newly created list is returned through `onReferenceListSelected`; the field
  draft stores `options_source_type="reference_list"` and the new
  `options_source_id`.
- `FieldEditorControl` receives the field hint and chooses the appropriate
  placeholder or compact fallback presentation for its control type.

No nested HTML forms are introduced. The reference screen and field form are
siblings under one editor root so submit and Escape behavior remain
unambiguous.

## Error and cancellation behavior

- Field validation remains local and Russian-first.
- Reference mutations display errors inside the reference screen and leave the
  field draft open.
- Empty reference-list and item names show explicit validation messages while
  keeping their actions available.
- `Назад` preserves the field draft and any successfully created or updated
  reference data.
- `Отмена` on the field screen discards only unsaved field changes; completed
  reference mutations are independent audited API actions and are not rolled
  back.
- Escape on the reference screen acts as `Назад`; Escape on the field screen
  keeps the existing field-editor cancellation behavior.

## Verification

Tests must cover:

- absence of a visible technical-code control and preservation of the original
  code in the field update payload;
- binary mandatory UI and conversion of both visible mandatory states to
  `required_on_publish` on save;
- collapsed public settings and unchanged saved values;
- hint persistence through `description`;
- placeholders and fallback hints for representative text, select,
  multi-select, date, and boolean filling controls;
- reference create validation, successful creation, automatic selection, and
  return to the preserved field draft;
- selected-list item create, rename, reorder, archive, localized denial, and
  explicit back navigation;
- no click-away field commit while the reference screen is active.

The existing skipped integration scenarios for inline reference creation and
selected-list item editing should be adapted and enabled rather than replaced
with weaker duplicate tests. Final verification uses the normal local gate,
server deploy checks, and a live browser pass through the exact inline field
workflow.

## Success criteria

- The compact field editor fits its field rectangle without a horizontal
  scrollbar at the supported editor width.
- Users do not see or edit a technical code in this workflow.
- Public settings are hidden until deliberately expanded.
- Mandatory fields follow the automatic draft/active lifecycle without a
  separate publish-time choice.
- A reference list and its items can be created or maintained without leaving
  the field editor, and returning does not lose the field draft.
- Card-filling users see the configured hint in or immediately within the input
  area.
