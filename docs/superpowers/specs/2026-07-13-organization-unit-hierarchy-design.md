# Внутренняя иерархия подразделений организации — дизайн

## Цель

Дать каждой организации собственное, отдельное от дерева организаций, дерево
управлений и отделов. Поле карточки `Подразделение организации` должно
предлагать только активные подразделения организации этой карточки.

## Границы

- Дерево `organizations` сохраняет только отношения между организациями и
  подведомственными организациями.
- Внутренняя структура использует существующую таблицу `org_units`, её REST
  API и тип поля `org_unit_ref`; новые параллельные таблицы не создаются.
- Внутренние подразделения не становятся отдельной границей RBAC. Доступ к
  ним определяется доступом пользователя к их организации.
- Изменения не удаляют карточки, поля или исторические значения.

## Допустимая структура

У каждой организации есть самостоятельное двухуровневое дерево:

```text
Организация
├─ Управление образования                 (управление)
│  ├─ Отдел дошкольного образования       (отдел)
│  └─ Отдел общего образования             (отдел)
└─ Отдел кадров                           (самостоятельный отдел)
```

- `Управление` всегда является корневым подразделением организации.
- `Отдел` может быть корневым подразделением или дочерним подразделением
  управления той же организации.
- Управление не может иметь родителя; управление внутри управления запрещено.
- Отдел не может быть родителем другого подразделения; глубина дерева не
  превышает двух уровней.
- Код подразделения уникален в пределах организации.

## Данные, API и аудит

`org_units` уже содержит `organization_id`, `parent_id`, `code`, `name`,
`type`, признак активности и архивную метку. После предварительной проверки
существующих записей миграция делает `type` обязательным и закрепляет два
допустимых значения: `management` и `department`. Если уже сохранённые данные
не соответствуют этой модели, развёртывание останавливается до изменения
данных; типы не угадываются и исторические записи не переписываются молча.

Сервис и REST API создают и обновляют подразделения только при соблюдении
структурных правил: родитель существует, активен, принадлежит той же
организации и имеет тип `management`; дочерним может быть только `department`.
Проверки выполняются на сервере до записи. Все create/update/archive операции
пишут `audit_events` с объектом `org_unit`.

Архивирование отдела делает его недоступным для новых выборов. Архивирование
управления каскадно архивирует все его активные дочерние отделы в одной
операции. Ссылки `cards.org_unit_id` и `field_values.value_org_unit_id` не
изменяются: прежние карточки по-прежнему показывают сохранённое значение с
архивным статусом, но новое значение выбрать нельзя.

## Поле карточки

В конструкторе шаблона тип `org_unit_ref` показывается пользователю как
`Подразделение организации`. У него нет настройки фиксированной организации.
При создании или редактировании карточки сервер и интерфейс получают список
только активных подразделений, у которых `organization_id` равен
`card.organization_id`.

Сервер отклоняет попытку записать в такое поле подразделение другой
организации или архивное подразделение. Отрисовка существующей карточки
отдельно разрешает историческую архивную ссылку, чтобы значение не исчезало.
То же правило применяется к публичному редактированию через уже разрешённые
поля карточки.

## Интерфейс администратора

В разделе `Организации` строка каждой организации получает раскрываемую
панель `Подразделения`. Она находится рядом с выбранной организацией, но
визуально отделена от подведомственных организаций.

- Панель показывает дерево с типовой меткой: `Управление` или `Отдел`.
- В корне выводятся управления и самостоятельные отделы; отделы управления
  вложены под него.
- `Добавить управление` создаёт корневое управление.
- `Добавить отдел` создаёт самостоятельный отдел либо отдел внутри выбранного
  управления из этой же организации.
- Изменение позволяет переименовать подразделение. Тип и родитель задаются
  при создании, поэтому уже созданное управление нельзя случайно превратить в
  отдел или переместить в другую структуру.
- Перед архивированием управления диалог явно называет все затрагиваемые
  дочерние отделы. Архивные элементы не показываются в активном дереве.

В карточке поле `Подразделение организации` — обычный выпадающий список.
Пустая карточка без организации не предлагает подразделения; после выбора
организации список содержит только её активные управления и отделы. Значение
архивного подразделения в существующей карточке показывается как архивное,
без возможности выбрать его заново.

## Ошибки и защита

- Нельзя создать подразделение в недоступной организации.
- Нельзя сделать управление дочерним подразделением, вложить отдел в отдел,
  указать родителя другой организации или архивного родителя.
- Нельзя записать в карточку подразделение другой организации либо архивное
  подразделение.
- Ошибки API отображаются в интерфейсе русским понятным текстом; технические
  коды не являются единственным объяснением ошибки.

## Проверка

Покрытие включает:

1. создание самостоятельного управления, самостоятельного отдела и отдела
   внутри управления;
2. отклонение запрещённых уровней и межорганизационных родителей;
3. каскадное архивирование управления, сохранность ссылок в карточках и
   исключение архивных элементов из новых вариантов;
4. серверную проверку `org_unit_ref` по организации карточки;
5. интерфейсное дерево, формы, предупреждение об архивировании и выпадающий
   список только для организации карточки;
6. RBAC и аудит для операций над подразделениями.
