# Автор карточки и идентификация в публичных ссылках

**Статус:** согласованное проектное решение, ожидает проверки перед реализацией
**Дата:** 17 июля 2026

## Цель

Показывать создателя карточки в базовом блоке и списке карточек. Для действий
через публичные ссылки запрашивать ФИО исполнителя до первого изменения и
сохранять это имя в истории конкретного изменения.

Решение не создаёт фиктивные учётные записи и не меняет действующие права
доступа.

## Термины и правила

- **Создатель карточки** — неизменяемый автор создания карточки.
  - Для внутреннего создания это существующий пользователь системы.
  - Для создания через публичную ссылку это ФИО, указанное при первом
    сохранении новой карточки.
- **Исполнитель публичного изменения** — ФИО, введённое посетителем публичной
  ссылки для конкретного изменения. Оно может отличаться от создателя карточки
  и никогда не заменяет его.
- В истории используется снимок ФИО на момент события, поэтому последующее
  изменение данных пользователя или новая запись в другой публичной сессии не
  меняют прошлые события.

## Модель данных

Новая миграция добавляет два nullable-поля длиной до 200 символов:

- `cards.public_creator_name` — ФИО создателя только для карточек, созданных
  через публичную ссылку. После первого сохранения не редактируется.
- `audit_events.actor_display_name` — отображаемое ФИО публичного исполнителя
  конкретного события. Это не идентификатор пользователя и не замена
  существующих полей `actor_user_id`, `actor_public_link_id` и
  `attributed_user_id`.

Для внутренней карточки отображаемое имя создателя определяется по
`cards.created_by` и имени пользователя. Для публичной карточки приоритет имеет
`public_creator_name`. Если исторические данные не позволяют определить автора,
интерфейс показывает `Не указан`.

Миграция не меняет существующие карточки и события: внутренние авторы будут
разрешаться по уже имеющемуся `created_by`, а старые публичные события без ФИО
останутся без персонального отображаемого имени.

## API и серверная проверка

### Карточки для внутреннего интерфейса

Ответы чтения карточки и строки списка получают поле
`creator_display_name`. Оно вычисляется сервером и используется в базовом блоке
и в таблице карточек. Клиент не передаёт и не редактирует это поле.

### Изменение существующей карточки по публичной ссылке

Каждый публичный изменяющий запрос получает обязательное поле `actor_name`.
Сервер нормализует пробелы, требует непустое значение не длиннее 200 символов и
отклоняет запрос без него. При успешном изменении сервер записывает
`actor_display_name` в аудит вместе с обычным безопасным diff.

Имя публичного редактора не меняет `cards.public_creator_name` и не меняет
`cards.created_by`.

### Создание карточки по публичной ссылке

Запросы, создающие черновик или выполняющие первое сохранение, также требуют
`actor_name`. При первом успешном создании карточки сервер записывает это имя в
`cards.public_creator_name` и в аудит создания. Последующие изменения дочерней
публичной ссылки требуют ФИО исполнителя и фиксируют его только в аудитном
событии.

То же обязательное требование применяется ко всем поддержанным публичным
операциям, меняющим карточку: значения полей, повторяемые блоки, вложения и
изменение статуса/отправка, если такие операции доступны из ссылки. Чтение
публичной ссылки остаётся доступным без ФИО.

Проверка выполняется на сервере; блокировка в интерфейсе — только удобный
ранний сигнал. Текст серверской ошибки отображается по-русски и не раскрывает
внутренние детали.

## Поведение интерфейса

### Внутренний интерфейс

- В «Базовом блоке» появляется строка `Создатель`.
- В списке карточек появляется столбец `Создатель`.
- Для текущих карточек в обоих местах показывается имя существующего
  пользователя-создателя; для публично созданных — сохранённое ФИО.

### Публичное создание и публичное редактирование

На обеих публичных страницах над карточкой расположен обязательный ввод `ФИО`.
Пока поле пусто, поля карточки остаются визуально доступными, но попытка кликнуть
или начать редактирование не открывает редактор и показывает поверх интерфейса
временную подсказку `Сначала укажите ФИО`.

После ввода ФИО редактирование работает как прежде. Имя хранится только в
состоянии текущей открытой страницы: после обновления страницы посетитель вводит
его снова. Это исключает сохранение заявленного имени в браузере и гарантирует,
что каждое изменение передаёт имя явно.

## Отображение аудита

В строках истории публичных изменений в колонке исполнителя отображается:

`Публичный пользователь: <ФИО>`

Внутренние события продолжают показывать системного пользователя. Если у
старого публичного события нет сохранённого ФИО, интерфейс использует текущий
безопасный нейтральный вариант отображения, не подменяя его данными создателя
ссылки.

## Безопасность и ограничения

- ФИО публичного посетителя — заявленное текстовое значение, а не
  аутентифицированная учётная запись.
- Авторство создания и исполнитель последующих изменений намеренно разделены.
- Автор карточки не редактируется через пользовательский интерфейс.
- Существующие RBAC-проверки, сроки жизни ссылок, правила аудита и безопасный
  diff сохраняются без ослабления.
- Новые значения не включаются в технический audit diff; для ФИО используется
  выделенное поле события.

## Проверка реализации

1. Миграция проходит на тестовой PostgreSQL базе; исторические строки остаются
   читаемыми.
2. Внутренне созданная карточка показывает пользователя-создателя в базовом
   блоке и списке.
3. Публичное создание без ФИО не создаёт черновик и возвращает русскую ошибку;
   с ФИО сохраняет автора карточки и аудит создания.
4. Публичное редактирование существующей карточки без ФИО не изменяет данные;
   с ФИО создаёт аудитное событие с этим ФИО и не меняет создателя карточки.
5. Два разных публичных исполнителя оставляют разные снимки ФИО в двух
   событиях, при этом создатель карточки остаётся прежним.
6. Фронтенд-тесты подтверждают блокировку с подсказкой, передачу `actor_name`,
   строку создателя, столбец списка и отображение публичного исполнителя в
   истории.
7. После локальных проверок выполняются стандартные проверка, развёртывание и
   браузерная проверка на стенде.

## Не входит в задачу

- регистрация или создание учётной записи для посетителя публичной ссылки;
- изменение создателя уже существующей карточки;
- предоставление дополнительных прав доступа по введённому ФИО;
- изменение данных старых аудитных событий задним числом.
